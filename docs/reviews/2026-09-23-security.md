### SEC-01 (High) — `DISTINCT ON (...)` expressions are never analysed

`AstDefaultMapper.selection()` in `pgsql-ast-parser` visits `from`, `columns`, `where`, `groupBy`,
`having`, `orderBy` and `limit`. It **never visits `val.distinct`**, which is typed
`'all' | 'distinct' | Expr[] | nil` — for `DISTINCT ON (a, b)` it holds a full expression list.
This is exactly the `over` bug, one node over.

Demonstrated (gate returns `ok: true`, `functions: []`):

```sql
select distinct on (pg_sleep(1)) a from t
select distinct on (pg_read_file('/etc/passwd')) a from t
select distinct on ((select 1 from pg_catalog.pg_tables)) a from t
select distinct on ((select 1 from information_schema.tables)) a from t
select distinct on (dblink('dbname=x','select 1')) a from t
with q as (select distinct on (pg_sleep(1)) a from t) select * from q
```

Verified against PGlite with `lockDown()` applied: the catalog form **executes**
(`select distinct on ((select count(*) from pg_catalog.pg_class)) a from t` returns rows). The
denied-function forms are stopped by layer 5 (`REVOKE EXECUTE` on the `learner` role), not by the
gate.

**Fix:** in `analyzeStatement()`, add a `select`/`selection` handler that, when
`Array.isArray(stmt.distinct)`, calls `visitor.expr(e)` for each entry — the same shape as the
`over` fix. Add the six inputs above to the malicious corpus.

### SEC-02 (High) — the `ON` clause of a JOIN attached to a function-call FROM item is never analysed

`AstDefaultMapper.fromTable()` and `fromStatement()` both visit `from.join`. `fromCall()` does not:
it calls `this.call(from)` (args / aggregate `orderBy` / `filter` / `withinGroup`) and drops
`FromCall.join` on the floor. So the `ON` predicate of
`... JOIN <set-returning-function>(...) ON <expr>` is learner-controlled SQL that reaches the engine
completely unanalysed.

Demonstrated end to end. The gate says `ok: true`, and the engine returns the value:

```sql
select * from t join generate_series(1,5000) g on g = (select count(*) from pg_catalog.pg_class)
```

PGlite (with `lockDown()` applied, `set role learner`) returned `[[1, 416]]` — the catalog row count
is read out of the sandbox through `g`. The `generate_series` range is chosen by the learner, so
this is a general numeric read channel; `substr(...) = 'x'`-style predicates turn it into a
per-character oracle for any `pg_catalog` / `information_schema` text. Other passing forms:

```sql
select * from t left join generate_series(1,3) g on pg_read_file('/etc/passwd') is null
select * from t right join generate_series(1,3) g on (select 1 from information_schema.tables) = 1
select 1 from t join unnest(array[1]) u on pg_sleep(1) is not null
```

Note the shape requirement: the call must be the FROM item **carrying** the join. `select * from t,
generate_series(1,3) g join u on pg_sleep(1) is null` is correctly blocked, because there the join
hangs off a `fromTable`.

**Fix:** in `analyzeStatement()`, add a `fromCall` (or `from`) handler that visits `from.join?.on`
before delegating to `map.super()`. Add the four inputs above to the corpus.

### SEC-03 (Low) — `FOR UPDATE / FOR SHARE` inside a sublink is not detected

`hasLockingClause()` recurses only through `union`, `with` and `from` items of type `statement`. A
locking clause in a scalar subquery, `EXISTS`, `IN (...)` or `ARRAY(...)` is missed:

```sql
select (select a from t for update) from u
select * from u where exists (select 1 from t for update)
select array(select a from t for update) from u
```

All three return `ok: true`. Layer 5 holds — PGlite answers `permission denied for table t`, because
`learner` has `SELECT` only — so there is no exploitable impact today, but the layer-4 control
listed in SQL_SANDBOX.md §4 ("locking clauses rejected") is not actually enforced for these shapes.
Cheapest correct fix: drop the hand-rolled walk and detect `for` inside the same `astVisitor` pass
via a `select`/`selection` handler.

### SEC-04 (Info) — `skipNonCode()` diverges from PostgreSQL's lexer, always in the safe direction

Three divergences exist; none is exploitable.

- **Nested block comments.** PostgreSQL (and `pgsql-ast-parser`) nest `/* ... /* ... */ ... */`;
  `skipNonCode()` stops at the first `*/`. The gate's comment region is therefore always a
  **subset** of the real one, so the gate can only ever treat _more_ text as code, never less.
  Confirmed: `select 1 /* /* */ , pg_sleep(1) */ from t` is accepted, and correctly so — the
  `pg_sleep` is inside the comment for the parser and for PostgreSQL alike.
- **Dollar-quote tags containing digits** (`$t1$`) are not recognised by the `^\$[A-Za-z_]*\$`
  probe. Irrelevant: `pgsql-ast-parser` rejects dollar quoting outright, so every such query fails
  closed with `parse_error` (verified for `$$...$$`, `$tag$...$tag$`, `$t1$...$t1$`).
- **`E'...\''` escape strings** end earlier for the gate than for PostgreSQL. Again the gate treats
  more text as code, and the only consequence is that a rewrite does not fire, which means the
  parser sees the original text and analyses _more_.

The "more text as code" direction can make `matchParen()` close a `WINDOW` clause early; every
attempt to weaponise that produced a `parse_error`, because the unblanked remainder is syntactic
garbage. It fails closed. Recorded here so the property is explicit rather than accidental.

## What was attacked and held

### D-18 · `normalizeSetOperators` — no finding

- It only ever substitutes one set-operator keyword for another, same length, padded with spaces,
  and the two-word forms are restricted to `[ \t]` so no newline is consumed. Positions are
  preserved (asserted by the existing tests, re-verified).
- Literals, quoted identifiers, line/block comments and dollar quoting are skipped via the shared
  `skipNonCode()`; `'intersect'`, `"except"`, `-- intersect`, `excepto` and `intersects` are all
  left alone.
- Word-boundary check on the preceding character plus `\b` in each pattern: `exceptunion` is not
  rewritten (and fails to parse).
- Semantics are irrelevant to the gate: whether the engine runs `EXCEPT` or the gate analysed
  `UNION`, both branches are parsed and both are visited. `select 1 except select pg_sleep(5)` and
  `select 1 intersect select * from pg_catalog.pg_tables` are still rejected.
- Execution uses the original SQL (`workerEngine.execute()` passes the caller's `sql`, not the
  rewritten text — verified in `src/lib/sandbox/engines/worker-engine.ts`).

No way was found to get a denied keyword, a call, or a statement separator through this rewrite.

### D-19 · `rewriteNamedWindows` and the probe — the escape argument holds

The author's claim is that the depth-balanced extraction makes early closure of
`select count(*) over (<definition>)` impossible. **Verified, with one correction to the
reasoning:** balance alone is not the guarantee. What actually closes the hole is that
`matchParen()` returns `-1` whenever a literal or comment is left open, so a definition can never
end inside an unterminated construct and the probe's trailing `)` can never be absorbed.

| Attempt                                                                      | Result                                                          |
| ---------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `window w as (partition by a -- )\n)`                                        | accepted; comment correctly ends at the newline, probe balanced |
| `window w as (partition by a /* ) */)`                                       | accepted; `)` stays inside the comment                          |
| `window w as (partition by $$ ) $$)`                                         | `parse_error` (dollar quoting unsupported)                      |
| `window w as (partition by $t1$ ) $t1$)`                                     | `parse_error`                                                   |
| `window w as (partition by $a1$'x'$a1$)`                                     | `parse_error`                                                   |
| `window w as (partition by e'\')`                                            | `parse_error`                                                   |
| `window w as (partition by a) )) select pg_sleep(1) --)`                     | `parse_error`                                                   |
| `window w as (partition by ')' ) order by pg_sleep(1))`                      | `parse_error`                                                   |
| `window w as (partition by a /* /* */ ) */ , pg_sleep(1) )` (nested comment) | `parse_error`                                                   |
| `window w as (partition by a) , x as (order by pg_sleep(1))`                 | `function_not_allowed`                                          |
| `window a as (...), b as (a order by pg_sleep(1))` (base-window name)        | `function_not_allowed`                                          |

An unterminated string or comment inside a definition makes `matchParen()` fail,
`readWindowClause()` returns `null`, nothing is blanked, and the `WINDOW` keyword reaches the
parser, which rejects it. The `synthetic.length !== 1` check is genuinely unreachable but correct
to keep.

Other properties re-verified: the rewrite fires only for names declared in a `WINDOW` clause, never
across a line break, never when the name is followed by `(` or `.`; `over` + `(` + padding + `)` is
exactly the length of `over` + whitespace + name; blanking preserves newlines so parser positions
stay truthful; a definition that fails to parse rejects the whole query; the probe call `count` is
stripped from `functions` so concept detection is not polluted.

### D-19 · `FRAME_BOUND` — grammar is closed

The only learner-controlled part of a bound is `'[^'\n]*'`: a complete single-quoted token with no
embedded quote and no newline, reachable only as `INTERVAL '...'` or `'...'::INTERVAL` immediately
followed by `PRECEDING|FOLLOWING`. Everything else is fixed keywords, `\s+`, or `\d+(\.\d+)?`.
Checked consequences:

- `'a''b'` (doubled quote) does **not** match — the bound fails, the clause is left in place, the
  parse fails. Fails closed.
- `1e3` is not matched by `\d+(\.\d+)?`; `parse_error`.
- `(select 1) preceding`, `'1'||pg_sleep(1) preceding` and `interval pg_sleep(1) preceding` are all
  rejected.
- `\s+` cannot span a comment, so nothing executable can hide between the tokens.
- The blanked span can only ever contain keywords, a number, or a string constant — never a call,
  an identifier or a subexpression — which is why, unlike a window definition, it does not need to
  be re-analysed.

One position-handling nit, not a finding: `stripWindowFrames()` tests `mask[offset]` only, i.e. the
**first** character of the match. A match cannot start in code and end inside a literal, because the
only literal in the grammar must be opened _and_ closed inside the match itself; and a match that
starts inside a literal is skipped (covered by an existing test). Correct as written; worth a
comment so the next reader does not have to re-derive it.

### D-19 · the `over` fix itself

Correct and sufficient for the node it covers. `CallOver` has exactly two expression-bearing fields
(`partitionBy`, `orderBy`), both now visited. Ordering matters and is right: the explicit
`visitor.expr(...)` calls happen **before** `map.super().call(c)`, so they do not collide with
`pgsql-ast-parser`'s `skipNext` flag. Re-confirmed blocked: inline `OVER (partition by pg_sleep(1))`,
`OVER (order by pg_read_file(...))`, `OVER (partition by (select ... from pg_catalog....))`, and the
same inside `filter (...) over (...)`.

### Nodes checked and confirmed visited

`FILTER (WHERE ...)`, `WITHIN GROUP (ORDER BY ...)`, aggregate inner `ORDER BY`, `LATERAL (...)`
bodies, `VALUES` lists (as a statement and in FROM), array subscripts, `CASE` value/when/then/else,
casts, row constructors and expression lists, `EXISTS` / `IN (subquery)` / `ARRAY(subquery)`
sublinks, function-call FROM item **arguments**, `WITH ORDINALITY` (carries no expression),
`BETWEEN` (ternary), `EXTRACT` / `SUBSTRING` / `OVERLAY`, `LIMIT` / `OFFSET`, `GROUP BY`, `HAVING`,
outer `ORDER BY`, both branches of a set operation, CTE bodies, `INSERT`/`UPDATE`/`DELETE` targets,
`SET` values, `RETURNING` and `ON CONFLICT` expressions.

**Not visited by the default traversal, and confirmed to matter:** `SelectFromStatement.distinct`
(SEC-01), `FromCall.join` (SEC-02), `ExprCall.over` (fixed by D-19). No others found.

## Pipeline integrity (SQL_SANDBOX.md §4)

No control was weakened to make D-18 or D-19 work. Verified by reading the code:

- Order is unchanged: size → UTF-8/null-byte → gate → worker with hard timeout → caps →

- **Execution uses the original SQL.** `workerEngine.execute()` and the browser engine call
  `gateSql(sql, ...)` for the decision and then pass the caller's `sql` to the worker; the rewritten

- One statement enforced; statement-kind allowlist and the DML-in-CTE rule unchanged; dollar

- `DENIED_FUNCTIONS` still comes from `sandbox-runtime/denied-functions.mjs`, shared verbatim with

- Layer 5 intact: `create role learner nologin`, `grant select`, `revoke create on schema public`,
  `REVOKE EXECUTE` on every denied function in `pg_catalog`/`public`, `set role learner` before each

- No new dependency; `src/lib/sandbox/**` does not import `src/lib/supabase/admin.ts`; no secret,

### SEC-05 (Low) — `FOR UPDATE` inside a named window definition is still not detected

`analyzeStatement()` now returns `locking`, but `gateSql()` only reads it for the main statement.
The window-definition loop keeps `inner.violation` (`violation ??= inner.violation`) and **discards
`inner.locking`**. The locking check also runs _before_ that loop, so even setting the flag there
would be too late.

```sql
select rank() over w from t window w as (partition by (select a from u for update))   -- ok: true
select rank() over w from t window w as (order by (select a from u for share))        -- ok: true
```

Both return `ok: true`. Every other shape SEC-03 listed is now correctly blocked, including ones the
old `hasLockingClause()` missed (sublinks, `EXISTS`, `ARRAY(...)`, `with recursive`,
`insert ... select ... for update`, `for update nowait`, `for update skip locked`). The new path is a
strict superset of the old one, so this is **not a regression** — the old walk never saw window
definitions either.

Impact today: none. Verified against the real engine as `learner`:
`select rank() over w from customers window w as (partition by (select id from orders for update))`
returns `permission denied for table orders`. Layer 5 holds, exactly as for the original SEC-03.

Fix (two lines): track it across the loop and move the check after it.

```ts
let locking = analysis.locking;
// inside the definitions loop:
if (inner.locking) locking = true;
// after the loop, still before `if (violation) return violation;`:
if (locking)
  return {
    ...base,
    code: "statement_not_allowed",
    statementType: statement.type,
    message: "Las cláusulas de bloqueo (FOR UPDATE/SHARE) no están permitidas.",
  };
```

Keeping the check ahead of `if (violation)` preserves the current priority (locking wins over a
schema or function violation found in the same statement).

### SEC-06 (Medium) — the schema allowlist is bypassed by simply omitting the schema

`pg_catalog` is implicitly first in `search_path` in every PostgreSQL session, so a learner never
needs to write it. The gate only rejects an **explicit** schema, so unqualified catalog relations
pass layer 4 untouched:

```sql
select * from pg_tables            -- ok: true, tables: ["pg_tables"]
select count(*) from pg_class      -- ok: true
select * from pg_settings          -- ok: true
select * from pg_roles             -- ok: true
select * from pg_type limit 1      -- ok: true
select * from t join generate_series(1,5000) g on g = (select count(*) from pg_class)  -- ok: true
```

Verified end to end against the worker engine as `learner`: `pg_class` (461 rows), `pg_settings`
(380 rows, incl. `listen_addresses`, `port`, `ssl`), `pg_roles` (18 rows with role names),
`pg_tables` (78), `pg_proc` (3413), `pg_user`. Credentials are **not** reachable — `pg_authid` and
`pg_shadow` return `permission denied`, and `current_setting()` is denied by the layer-5 REVOKE.

So the exposure is metadata of an ephemeral, single-tenant, in-process PGlite holding only public
dataset data: no learner data, no secrets, no cross-tenant reach. That is why this is Medium and not
High. But note the consequence for the previous review: **SEC-02 was never the only catalog read
channel** — `select ... on g = (select count(*) from pg_class)` reads the same value without any
schema qualifier, and still does. The SEC-02 fix is correct and worth keeping; its severity rating
assumed a schema allowlist that was already porous.

Options for the owner (either way this needs a DECISIONS.md entry — it is a documented §4 control):

1. Reject unqualified relation names matching `^pg_` plus the `information_schema` view names in
   `tableRef` (cheap, no false positives — the dataset generator never emits `pg_*` table names),
   with an educational Spanish message.
2. Accept explicitly, on the grounds that the sandbox instance contains nothing private and is
   destroyed per request, and amend the §4 wording in `docs/SQL_SANDBOX.md` so the control is not
   overstated ("system schemas denied" currently reads as a guarantee it does not provide).

A smaller instance of the same "PostgreSQL resolves it for you" pattern: cast targets are a catalog
read channel the gate does not model at all — `select 'customers'::regclass::oid`,
`select 'public'::regnamespace::text` and `select 1::oid::regrole::text` all pass the gate and
execute. Same exposure class; subsumed by whichever option is chosen.

### SEC-07 (Info) — three positions in the traversal walker do not plant the payload where their name says

Not a security gap; a coverage-accuracy gap in a file whose whole purpose is to be trustworthy about
coverage.

- `"AT TIME ZONE operand"` — `select a at time zone 'UTC' from t where b = ${x}`. The payload lands
  in `where`; the `AT TIME ZONE` node never receives one. Duplicate of `"binary right operand"`.
  (Harmless: `AT TIME ZONE` is an ordinary `ExprBinary`, both operands visited — probed directly with
  the payload in each operand, both blocked.)
- `"JOIN USING, where"` — payload in `where`; `JoinClause.using` is `Name[]` and can never carry an
  expression, so there is nothing to test there.
- `"WITH ORDINALITY FROM item"` — payload in `where`; `FromCall.withOrdinality` is a boolean.

Also duplicates of an already-covered node rather than new positions: `"FETCH FIRST"` →
`LimitStatement.limit` (same node as `"limit"`); `"GROUP BY ROLLUP"`, `"GROUP BY CUBE"`,
`"ANY (array)"`, `"ALL (subquery)"` and `"POSITION(... in ...)"` all parse to an ordinary `ExprCall`
argument; `"CROSS JOIN LATERAL body"` → `FromStatement.statement`; `"lateral function-call FROM item
argument"` → `FromCall.args`. The 86 positions map to roughly 55 distinct AST fields — worth saying
in the file header so the number is not read as node coverage.

Two smaller notes on the same file:

- `noQualifiedRef` on `"function-call FROM item argument"` is unnecessary and masks a check that
  passes: `select * from generate_series(1, pg_catalog.pg_tables.tablename)` parses and is correctly
  rejected with `schema_not_allowed`. Remove the flag.
- `unseenNodes()` compares call names against a `Set`, so it checks presence, not multiplicity. If a
  future template ever plants the same function name twice (once in a visited position, once in an
  unvisited one), the walk would not notice. Comparing sorted multisets would close that.

## Independent audit of the completeness claim

I walked every `Expr`-bearing and `QName`-bearing field of every node reachable from
`select` / `union` / `union all` / `values` / `with` / `with recursive` / `insert` / `update` /
`delete` in `syntax/ast.ts`, against the corresponding `AstDefaultMapper` method.

**Agreement in substance, disagreement in letter.** The claimed set (`ExprCall.over`,
`SelectFromStatement.distinct`, `SelectFromStatement.for`, `FromCall.join`, `ExprRef.table`,
`OnConflictAction.where`) is correct as far as it goes and is complete for everything that can carry
an expression or a statement. It is missing three unvisited fields:

| Field                                        | Content                                   | Channel | Probe                                                                                                                                                              |
| -------------------------------------------- | ----------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ExprBinary.opSchema` / `ExprUnary.opSchema` | schema string, from `OPERATOR(schema.op)` | none    | `select 1 operator(information_schema.+) 1` → gate `ok: true`; engine: `operator does not exist`                                                                   |
| `OnConflictOnConstraint.constraint`          | `QName` (schema + name)                   | none    | `insert into t (a) values (1) on conflict on constraint information_schema.c do nothing` → gate `ok: true`; PostgreSQL does not accept a qualified constraint name |
| `SelectFromStatement.skip`                   | `'nowait' \| 'skip locked'`               | none    | not reachable without `for` (`select a from t skip locked` → `parse_error`); moot once `for` is detected                                                           |

None carries an `Expr` or a `Statement`, so none is exploitable; they belong in the documented list
for the next auditor, not in a fix.

`ExprConstant.dataType` is a non-issue for a different reason: the parser never produces it for
learner input. `select date '2020-01-01'` and `select information_schema.cardinal_number '1'` both
parse as `{type:'cast', to:{...}}`, so that field collapses into `ExprCast.to`.

### The `ExprCast.to` dismissal is correct

"A type name cannot carry a call or a subquery" holds in this parser, in every form I could build.
`DataTypeDef` is `ArrayDataTypeDef | BasicDataTypeDef`; `ArrayDataTypeDef` recurses only into another
`DataTypeDef`, and `BasicDataTypeDef` is `QName` plus `config?: number[]` plus `doubleQuoted?`.
Probed and confirmed:

| Form                                                        | Result                                                                          |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `select 1::pg_catalog.int4[]`                               | `to: {kind:'array', arrayOf:{schema:'pg_catalog', name:'int4'}}` — strings only |
| `select 1::int4[][]`                                        | nested `array`/`arrayOf`, still strings only                                    |
| `select 1::"pg_catalog"."int4"`                             | `doubleQuoted: true`, strings only                                              |
| `select 1::"weird type"`, `select 1::pg_catalog.setof int4` | accepted, strings only                                                          |
| `select 1::numeric(pg_sleep(1))`                            | `parse_error` — `config` accepts digits only                                    |
| `select 1::numeric((select 1 from pg_catalog.pg_class))`    | `parse_error`                                                                   |
| `select cast(1 as pg_catalog.int4 array)`                   | strings only                                                                    |

So `to` is an **unchecked schema** (`select '1'::information_schema.cardinal_number` passes) but not
a traversal bypass. The residual risk is the `reg*` cast channel described under SEC-06, which is a
PostgreSQL-semantics issue rather than a parser-traversal one; visiting `to` in the `cast` handler
would close the schema half of it cheaply and is worth doing whichever SEC-06 option is chosen.

## Controls, ordering and priority

- **Priority is unchanged.** The old order was statement-kind → `hasLockingClause()` → visitor
  violations. It is now statement-kind → `analyzeStatement()` → `analysis.locking` →
  window-definition analyses → `violation`. Confirmed by probe: `select pg_sleep(1) from t for
update` → `statement_not_allowed` (locking message); `select a from pg_catalog.x for update` →
  `statement_not_allowed`; `select pg_sleep(1) from pg_catalog.x` → `schema_not_allowed` (first
  violation wins, as before). The only change is that a window-definition violation is evaluated
  after the main locking check — the same relative order as before.
- **The `skipNext` ordering rule does not apply here, and nothing depends on it.** `astVisitor` does
  not use the mapper's `skipNext` flag: `Visitor.super()` returns a `SkipVisitor` that applies the
  default implementation with the _visitor_ as `this`, so nested nodes re-dispatch to the handlers
  and the flag is never set. Explicit visits are therefore safe before or after `map.super()`. What
  does matter is double-counting, and there is none: for each explicit visit the corresponding
  default method provably does not touch that field (`selection` ignores `distinct` and `for`,
  `fromCall` ignores `join`, `insert` ignores `onConflict.where`, `call` ignores `over`, `ref` is a
  leaf). Confirmed empirically — `select distinct on (abs(1)) a from t` reports `functions: ["abs"]`,
  not `["abs","abs"]`; same for the join, on-conflict and over positions.
- **No control weakened.** `DENIED_FUNCTIONS` still sourced from
  `sandbox-runtime/denied-functions.mjs`; `ALLOWED_SCHEMAS` still `{public}`; one-statement rule,
  statement-kind allowlist and the DML-in-CTE rule unchanged; execution still uses the original SQL
  (`workerEngine.execute` passes the caller's `sql`); `src/lib/sandbox/**` still imports nothing from
  `src/lib/supabase/admin.ts`; no new dependency; no secret, token or env value touched or logged.
- **Layer 5 re-verified in this session** on the real worker: `set role learner`, writes denied
  (`permission denied for table customers`), `FOR UPDATE` denied, `current_setting` denied,
  `pg_authid` / `pg_shadow` denied.

## The regression walker: does assertion 1 really guard?

Yes, for every entry — and assertion 2 is the stronger guard.

- Assertion 1 iterates **all** `expressionPositions` with no `continue`, collects failures and asserts
  `[]`. A template that does not parse shows up there as `parse_error`.
- Assertion 2 additionally requires the planted `abs` to appear in `GateResult.functions` for every
  position, which is what catches an unvisited node even when the payload is not itself denied. A
  position that is a no-op _for the gate_ (payload swallowed into a literal or comment) fails here.
- Assertions 3–5 require a **specific** code (`function_not_allowed` / `schema_not_allowed`), not
  merely `!ok`, so a template that parses with the harmless payload but not with the denied one fails
  rather than passing silently. This is the right shape; it is easy to get wrong.
- Both skip flags fail closed and were checked by hand: `noSublink` on `"FETCH FIRST"` —
  `select a from t fetch first (select 1 from pg_catalog.pg_tables) rows only` is a `parse_error`, and
  the same position with a denied function or a qualified ref _is_ rejected, so the position is still
  covered two ways; `noQualifiedRef` is unnecessary (SEC-07).
- Limitations worth knowing, none of them a false pass: the reflection walk (assertion 8) runs over
  `GateResult.ast`, which is the **rewritten** AST — named-window definitions have been blanked out of
  it, so that assertion cannot see inside them (assertions 1–5 do cover those two positions). The walk
  also only recognises `type: 'call' | 'table' | 'ref'`, so `insert`/`update`/`delete` target `QName`s
  and `ExprCast.to` schemas are invisible to it; the table-position tests cover the former, and the
  latter is SEC-06.

What no position exercises, and what a future reviewer should add if the grammar grows: nothing in
the allowed statement kinds that I could find. Beyond the corpus I probed grouping sets,
`TABLESAMPLE`, `MERGE`, `ROWS FROM`, `COLLATE`, `SIMILAR TO`, `IS DISTINCT FROM`, `BETWEEN SYMMETRIC`,
`ORDER BY ... USING`, `XMLELEMENT`, `JSON_TABLE`, `TABLE <name>` and `trim(... from ...)` — every one
is a `parse_error` (fails closed), which is why they are not positions.

only from `worker-engine.ts`, `browser-engine.ts` and `exercises/service.ts`, all on learner SQL, and
the dataset load plus `lockDown()` run as the instance owner before the role is ever assumed. Its
`p.oid::regprocedure` is a cast, so no EXECUTE is consulted, and an owner's privileges cannot be
reduced by `REVOKE ... FROM public, learner` in any case. Verified by running `lockDown()` **twice**
on the same instance: idempotent, no error, learner SQL unaffected afterwards.

**4. No evasion of the prefix rule found.** 26 hostile spellings were put through `gateSql`, all
rejected: quoted (`"pg_sleep"(1)`, `"regclass"('customers')`, `'customers'::"regclass"`), mixed case
(`PG_Sleep`, `Pg_Show_All_Settings`, `PG_Settings`), `pg_catalog`-qualified in both the function and
the cast position (`pg_catalog.regclass(...)`, `'customers'::pg_catalog.regclass`), array cast
(`::regclass[]`), a set-returning catalog function in `FROM` and in a `JOIN`, and the same calls
buried in a CTE, a `LATERAL`, a scalar subquery, a `DISTINCT ON`, an `OVER (PARTITION BY ...)` and a
named window definition. 9 legitimate spellings were confirmed still accepted: `regexp_replace`,
`regr_slope` / `regr_r2`, a table named `region`, a column named `registro`, `to_char` / `to_date` /
`to_number` / `to_timestamp`, and aliases named `pg_*` (an alias is not a relation name). The one
spelling the gate lets through by design, `public.to_regclass('customers')`, was executed on the
engine: it does not resolve (`function public.to_regclass(unknown) does not exist`) and the learner
cannot create it (`permission denied for schema public`, verified for both `create table` and
`create function`). Operator syntax (`operator(pg_catalog.+)`) works, as documented, and reaches only
operators, whose underlying functions are privilege-checked normally.

**5. No regression against SEC-01..SEC-07.** The traversal regression walker, the 279-input fuzz
corpus, and the engine, timezone and catalog suites are green (41/41, run in this pass, not taken on
report), and the `DISTINCT ON`, `FromCall.join.on`, sublink-locking, `skipNonCode` and
window-definition-locking behaviours were spot-checked by hand as well.

### SEC-10 (Info) — "layer 5 is what holds" was true for functions and false for relations

§4 closed its catalog paragraph with: _a catalog relation or function whose name matches none of
these prefixes — this is a name-based control at layer 4, and layer 5 is what holds._ For the
function spelling that is accurate (EXECUTE is revoked; verified). For the **relation** spelling it is
not: PostgreSQL grants `SELECT` on most system catalogs to `PUBLIC`, and after `lockDown()` the
`learner` role still read `pg_class` (420 rows), `pg_proc` (3 413), `pg_roles` (18) and `pg_tables`
(69). Only `pg_authid`, `pg_shadow`, `pg_statistic`, `pg_file_settings` and `pg_stat_activity` failed
on permissions, plus `information_schema` (its views call `pg_has_role`, which the new prefix
`REVOKE` happens to have taken out — an unintended hardening with no curriculum cost).

This opens nothing today, because the relation rule is in fact complete: **every** relation in this
engine's `pg_catalog` is named `pg_*` (queried: zero exceptions), so the gate's `^pg_` covers all of
them, and `information_schema` is denied by schema. But the sentence would have told a future
engineer that a missed relation name is caught downstream, and it is not. §4 now states which half of
the claim layer 5 backs, names the catalogs that remain readable, and says that what makes the
relation rule complete is the naming convention rather than the permission. No code change.

## What the sandbox does and does not guarantee — for the owner

Plain version, with no reassurance that was not measured.

**What it guarantees.**

- Learner SQL never touches the application database. It runs in a separate in-memory PostgreSQL
  (PGlite) loaded with the exercise dataset only — no user row, no payment record, no secret is in
  that instance. If a learner broke every control in the gate, what they would be standing in is a
  throwaway copy of a fictional business dataset.
- One statement per submission, only the statement kinds the exercise allows, and DML hidden in a CTE
  counts as DML. No transaction control, no DDL, no `COPY`, no `SET`.
- The execution role is `learner`: `SELECT` only, no `CREATE` in `public` (verified: it cannot create
  a table or a function), EXECUTE revoked on the dangerous-function list and on every `pg_*` /
  `to_reg*` function in `pg_catalog` (~458 in this build).
- A query that will not stop is stopped: PGlite ignores `statement_timeout`, so the worker process is
  killed at 5 s and respawned. Result size is capped (1 000 rows, 100 columns, 2 KB per cell).
- Error text shown to the learner is the Postgres message, hint and position only — no stack trace and
  no file path.
- Hints, solutions and expected results are never sent to the browser before they are unlocked.

**What it does not guarantee.**

- The system-catalog block is a **name** rule. Relations are blocked because their names start with
  `pg_`, functions because they start with `pg_` or `to_reg`, and the eleven OID alias types are an
  exact list. Those rules match everything this engine ships — which is now asserted by a test that
  boots the real engine and compares, so a PGlite upgrade that adds a name fails CI instead of passing
  silently. But it is still a name rule, and a differently-named catalog object added upstream would
  slip past it until that test catches it.
- For **one** spelling, `regclass('customers')`, the gate is the only control that exists. PostgreSQL
  treats it as a cast rather than a function call, so no permission is consulted and no `REVOKE` can
  stop it. If that rule were ever removed, nothing behind it would catch the query.
- Layer 5 does **not** stop a learner from reading `pg_class`, `pg_proc`, `pg_roles` or `pg_tables` if
  the gate is bypassed — those catalogs are world-readable in PostgreSQL by design. What such a read
  exposes is the dataset's own metadata, the engine version and role names. Not learner data, not
  credentials.
- The parser gate rests on `pgsql-ast-parser`, which is not PostgreSQL's parser. Three grammar gaps
  (frame clauses, `INTERSECT`/`EXCEPT`, named windows) are handled by rewriting the text before
  analysis; each rewrite is length-preserving, never applies inside strings or comments, and the
  **original** SQL is what executes. Four passes have attacked those rewrites without finding a way to
  smuggle syntax through them, but "not found in four passes" is not "proven impossible".
- Resource exhaustion is bounded per query, not per user: a learner can send query after query, each
  costing up to 5 s of a worker. Rate limiting, not the sandbox, is what stops that, and it deserves a
  second look once there is real traffic.

**The residual risk being accepted by launching:** an attacker who defeats the gate's name rules could
read system-catalog metadata of a throwaway database that contains only exercise data, and could burn
CPU up to the timeout. They cannot reach user data, the application database, or any secret, because
none of those exist inside the instance where their SQL runs. That is a reasonable trade for a product
whose entire purpose is to let strangers run SQL, and it is the risk these four passes have been
narrowing.
