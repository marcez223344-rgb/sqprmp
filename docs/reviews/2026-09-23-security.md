# Security and privacy review — 2026-09-23

Reviewer: `security-engineer`. Scope: everything changed in the 2026-09-23 working session (admin user
directory, sandbox engine wrapper, comparator value feedback, per-question quiz grading, leaderboard,
draft autosave, exercise→lesson progress sync) plus a routine sweep of the whole diff.

Authoritative rules applied: `CLAUDE.md` (non-negotiables 1–10), `.claude/rules/security.md`,
`docs/SECURITY.md` §§2–7.

## Verdict up front

**Nothing found in today's work must be fixed before committing it.** No secret, no token, no PII
leaves a trust boundary that it did not already cross, no RLS policy was widened, and every new
migration and server path holds up under the checks below.

Two things must be fixed before the features they belong to are switched on, and one of them is
older than today:

- **F-1 (High, pre-existing):** the answer key of all 27 `matching` questions is readable by
  anonymous visitors through `public.questions_public.pairs`. Fix before the quiz/certificate flow is
  presented as an assessment.
- **F-2 (High):** `answerReviewQuestionAction` hands the correct answer and explanation for **any**
  published question to any signed-in learner, without requiring that they ever answered it. Fix
  before certificates are promoted as verifiable.
- **F-3 (Medium):** the leaderboard publishes `level` and `xp`, while the consent text promises
  "alias and avatar only", and the RPC is callable by `authenticated` even with the `leaderboards`
  flag off. **Blocks enabling the flag.**

## Findings

### F-1 · High · Matching-question answer key is public — `supabase/migrations/20260918190000_curriculum.sql:281`

```sql
create or replace view public.questions_public with (security_invoker = true) as
  select q.id, …, q.pairs, q.tags, q.estimated_seconds
  from public.theory_questions q where q.is_published;
grant select on public.questions_public to anon, authenticated;
```

`pairs` **is** the grading key for `matching` questions: `correctAnswerFor()` builds the expected
answer as `Object.fromEntries(pairs.map(p => [p.left, p.right]))`
(`src/lib/quizzes/service.ts:210`). The server shuffles the right-hand column before delivery
(`hydrate()`, `service.ts:118`), but the un-shuffled pairing is one PostgREST call away
(`/rest/v1/questions_public?select=pairs`) — with the anon key, no session needed. 27 questions in
`src/content/questions/**` are of this type.

This violates CLAUDE.md rule 7 and `.claude/rules/security.md` ("`question_options.is_correct` … are
served only by server code"). It is pre-existing (2026-09-18), not introduced today, but today's work
built immediate per-question reveal on top of this surface, so it belongs in this report.

Secondary, same view: the grant to `anon` also publishes every quiz prompt of every section,
including paid ones (`is_published` is filtered, `is_free` is not).

**Fix:** drop `pairs` from the view and let `loadBank()` read it with the admin client (it already
runs server-side and already shuffles), or expose two independent arrays (`left_labels`,
`right_candidates_shuffled`) instead of the paired JSON. While there, restrict the view to
`authenticated` unless an anonymous preview is actually needed.

**Blocks release?** Does not block committing today's work. **Blocks presenting quizzes/certificates
as an assessment** — a passing score is currently obtainable without knowing SQL.

### F-2 · High · Review grading is an unrestricted answer-key oracle — `src/lib/quizzes/service.ts:592`

```ts
export async function gradeReviewQuestion(profile, questionId, answer) {
  if (!(await consume(`quiz_answer:${profile.id}`, limits.rateLimits.submit))) return null;
  …
  const { data: visible } = await supabase.from("questions_public").select("id").eq("id", questionId)…
  const key = (await answerKeys([questionId])).get(questionId);
  return buildFeedback(key, answer, gradeAnswer(key, answer));
}
```

The only checks are "signed in" and "the question is published". There is no check that the learner
previously answered this question (which is what "review" means, and what
`getReviewQuestions()` at `service.ts:563` actually selects). Any learner can enumerate question ids
from `questions_public` and call `answerReviewQuestionAction` (`src/lib/quizzes/actions.ts:76`) with
`null` to receive `correctAnswer`, `explanation_md` and `whyIncorrect_md` for the entire bank at
30 calls / 5 min. Note `answerReviewQuestionAction` does not even require
`onboarding_completed_at`, unlike the graded path.

This is a rewrite of a pre-existing hole (the old `submitReviewAction` graded up to 60 arbitrary ids
per call, so today's version is a 25× improvement) — but it still defeats the per-attempt reveal
control that D-34 depends on, and quiz passes gate section completion and certificate eligibility.

**Fix:** require ownership before revealing.

```ts
const { data: own } = await createAdminClient()
  .from("quiz_answers")
  .select("question_id")
  .eq("user_id", profile.id)
  .eq("question_id", questionId)
  .limit(1)
  .maybeSingle();
if (!own) return null;
```

One query, and it makes the endpoint match its own doc comment. Keep the rate limit.

**Blocks release?** Does not block the commit. **Must be fixed before certificates are marketed as
verifiable**, and before F-1 is fixed it is the cheaper of the two attacks, so fix both together.

### F-3 · Medium · Leaderboard exceeds its consent text and ignores the feature flag — `supabase/migrations/20260923121000_leaderboard.sql:72`, `src/messages/es-419.json:314`

Two distinct problems in one feature.

1. **Consent scope.** The profile checkbox hint reads: _"Solo se mostrará tu alias y avatar. Puedes
   desactivarlo cuando quieras."_ The board actually publishes `alias`, `avatar_path`, **`level`** and
   **`xp`** (lifetime and a 7-day window, i.e. a recent-activity signal) —
   `leaderboard.sql:19-26`. `docs/SECURITY.md` §7.2 likewise still says public surfaces show "alias or
   chosen certificate name only". The disclosure is larger than what the learner agreed to.
2. **The flag is not an access control.** `grant execute on function public.leaderboard(text, integer)
to authenticated` means any signed-in learner can read the board directly through PostgREST while
   `features.leaderboards` is off and `/ranking` returns 404 (`src/app/(learn)/ranking/page.tsx:42`).
   Combined with (1), data is already readable under a consent statement that does not cover it.

**Fix:**

- Consent text is owner-approved copy, so route it through `docs/OWNER_ACTIONS.md`: proposed wording
  names alias, avatar, level and accumulated XP, and says the board is visible to other signed-in
  learners. Update `docs/SECURITY.md` §7.2 in the same change. Do not change it silently.
- Either `revoke execute … from authenticated` and call the two RPCs with the admin client after
  `isLeaderboardEnabled()` (keeps the flag authoritative and keeps the consent filter in SQL), or add
  `and exists (select 1 from public.feature_flags where key = 'leaderboards' and enabled)` inside the
  function. The first is cleaner: `src/lib/progress/leaderboard.ts:63` already checks the flag at the
  page level, it just uses the learner-scoped client — if you switch to the admin client, pass the
  timezone and the self id explicitly instead of relying on `auth.uid()`.

**Blocks release?** **Blocks enabling the `leaderboards` flag.** Does not block the commit (flag off,
route 404s).

Everything else the author claimed about the leaderboard is confirmed correct — see "Verified" below.

### F-4 · Medium · The comparator's expected-cell example is a workable answer oracle — `src/lib/validation/compare.ts:408`

The deliberate decision (one expected cell for one row, or a ratio/offset hint) is _directionally_
right: it is strictly less than the `exampleExpectedRow` it replaced, and the `singleCellAnswer`
guard correctly suppresses the value when the whole result is one cell. My concern is the iterated
case, which the guard does not cover.

Concrete extraction path, using only documented behaviour:

1. The expected row count is learnable from the existing row-count findings.
2. Select **only the target column** (`select 0 as revenue from generate_series(1, N)`). Then
   `comparableNames = ["revenue"]`, `keyIdx` is empty, and rows are paired **by position**
   (`compare.ts:214`).
3. `differing[0]` (`compare.ts:223`) is the first positional mismatch, so the message returns the
   expected value of row 1.
4. Feed the now-known value back and put the probe in row 2. One submission per cell, in order.

`rateLimits.submit` is 30 per 5 min (`src/config/limits.ts:101`), i.e. 360/hour: a 4-column ×
18-row expected result is ~72 submissions, about 12 minutes of scripted requests. The result is not
another user's data and not a secret — it is the exercise's expected output — but it lets a learner
reconstruct the answer without writing the query, which is the thing rule 7 exists to prevent.

**Fix (cheap, keeps the pedagogy):** gate the literal value on the learner having actually attempted
the full shape of the answer. In `compareResults`, where the finding is pushed:

```ts
const narrowed = missingColumns.length > 0 || comparableNames.length < wantedNames.length;
// …
messageKey: singleCellAnswer || narrowed ? "cell_values_example_actual" : "cell_values_example",
```

That alone removes the single-column oracle (step 2 becomes useless) and costs nothing for an honest
learner, who selects every expected column. Optionally also cap it: show the literal expected value
at most once per exercise per N genuine attempts, and prefer the ratio/offset hint (which reveals no
absolute value) when both are available — today the pattern branch already wins when it fires, which
is the right precedence.

**Blocks release?** No. Recommended in this session because the guard is three lines.

### F-5 · Low · Admin RPC guards fail open when there is no JWT subject — `supabase/migrations/20260923150000_admin_user_directory.sql:76` and `:198`, `20260923160000_quiz_pass_rate_submitted.sql:116`

```sql
if auth.uid() is not null and not public.is_admin() then raise exception … '42501'; end if;
```

For a `service_role` call `auth.uid()` is null, which is the intent. But it is also null for an
**anon** call (publishable key, no session), so for that caller the guard does nothing and the only
protection is the `revoke execute … from public, anon, authenticated`. The revocation is correct and
present, so this is not exploitable today — it just means the "defense in depth if a grant is ever
widened" claim in the migration header does not hold for the anon case.

**Fix:** assert the role instead of the absence of a user:

```sql
if not public.is_admin()
   and coalesce(nullif(current_setting('request.jwt.claims', true), '')::jsonb ->> 'role', '')
       <> 'service_role'
then raise exception 'admin only' using errcode = '42501'; end if;
```

**Blocks release?** No.

### F-6 · Low · `finishQuizAction` has no rate limit — `src/lib/quizzes/actions.ts:55`

`answerQuestionAction` is rate-limited; the finalizer is not. On an already-submitted attempt it
still runs `finalize_quiz_attempt` → `award_reward` → `check_section_completion` →
`evaluate_badges` on every call. Nothing is double-paid (`award_reward` is keyed
`quiz_passed:<lesson_id>`, `finalize_quiz_attempt` returns the stored row) — this is DB work
amplification, not an integrity hole.

**Fix:** `if (!(await consume(\`quiz_finish:${profile.id}\`, limits.rateLimits.quizAnswer))) return { ok: false, error: "rate_limited" };`

**Blocks release?** No.

### F-7 · Low · Quiz-answer rate limit borrows `rateLimits.submit`; here are the numbers I want

Current: `consume("quiz_answer:<uid>", limits.rateLimits.submit)` = 30 tokens / 5 min, shared between
the graded attempt path and review practice (`service.ts:369` and `:597`).

30/5 min is _adequate_ for honest use and _too generous_ for the F-2 farming path. Recommended, to be
added to `src/config/limits.ts` and documented in `docs/SECURITY.md` §5:

```ts
/** One graded quiz answer. A 6-question attempt costs 6; 20 allows three full quizzes in five
 *  minutes, which is more than any honest learner does and far short of farming a 300-question bank. */
quizAnswer: { capacity: 20, refillPerSecond: 20 / 300 },
/** Review practice is untimed and unrewarded, so it can be looser than the graded path. */
quizReview: { capacity: 30, refillPerSecond: 30 / 300 },
```

Use `quizAnswer` for `answerQuizQuestion` and `finishQuizAction`, `quizReview` for
`gradeReviewQuestion` — and keep the separate bucket keys, which the author already got right.

**Blocks release?** No.

### F-8 · Low · Sign-out leaves learner SQL in `localStorage` — `src/components/workspace/use-draft-autosave.ts:28`, `src/app/auth/signout/route.ts`

`dms.draft.<slug>` → `{sql, savedAt}`, unencrypted, no expiry, never cleared. Assessment: storing it
is **acceptable** — it is the learner's own work, it contains no credentials and no third party's
data, and the alternative (losing a finished query) is the problem this hook was written to solve.
`docs/SECURITY.md` §7.1 lists "Attempts / SQL text" as account-lifetime data already.

What is not acceptable is that on a shared machine the next person to use the browser can read the
previous learner's queries, and the key names disclose which exercises they were working on. The
sign-out route is a server POST, so it cannot touch `localStorage`.

**Fix (both parts, small):**

1. Namespace the key by user: `dms.draft.<userId>.<slug>`. Then a second account on the same browser
   can never read or resume the first one's drafts even if cleanup fails.
2. Clear on sign-out from the client that triggers it: in the sign-out form's `onSubmit`
   (`src/components/layout/app-header.tsx`), before submitting,
   `for (const k of Object.keys(localStorage)) if (k.startsWith("dms.draft.")) localStorage.removeItem(k);`
   Belt and braces: do the same sweep on mount of the sign-in page.

**Blocks release?** No. Worth doing before the first shared-device user exists.

### F-9 · Low · `getUserDetailAdmin` passes an unescaped search term — `src/lib/admin/queries.ts:246`

`p_search: userId` goes into `admin_user_directory` without `escapeLikeTerm()`, unlike
`listUsersAdmin`. Today the only caller validates against `/^[0-9a-f-]{36}$/`

get _some other_ profile's age / access class / activity rendered on a detail card next to the

inside the admin panel.

**Fix:** match by id explicitly (`p_search: userId` → keep, but wrap in `escapeLikeTerm()`), or add a
`p_user_id uuid` parameter to the function for exact lookups.

**Blocks release?** No.

### F-10 · Info · Audit-log target filter — `src/lib/admin/queries.ts:143`

`q.or(\`target_id.eq.${filter.target},target_table.eq.${filter.target}\`)`interpolates into a

### F-11 · Info · Notes that are not defects

- **k-anonymity of `admin_user_stats`.** A `by_country` bucket with one learner does identify that
  learner — but the same page's sibling (`/admin/usuarios`) lists every learner by name anyway, and
  both are gated by `requireAdmin()`. No suppression is needed while these numbers stay admin-only.
  `MIN_LEARNERS_FOR_RATES` (`src/lib/admin/directory.ts:45`) suppresses _ratios_, not counts, so it is
  not a privacy control and should not be mistaken for one: if any of these aggregates is ever put on
  a public page, small-cell suppression has to be added there.
- **`leaderboard(p_period, p_limit)`** clamps `p_limit` only at the bottom (`greatest(…, 1)`), so a
  caller can request the whole board. Every row is opt-in, so this is not a leak — but "top 25" is a
  display choice, not a limit.
- **Consent has no timestamp.** `leaderboard_opt_in` is a bare boolean; `terms`/`privacy` consent is
  versioned with timestamps. For a disclosure to other users, recording _when_ the learner opted in
  (and out) is worth the one column.
- **`saveDraftAction`** has no rate limit. It writes only the caller's own row via an
  `auth.uid()`-scoped RPC and is debounced at 6 s, so this is cosmetic.

### 2. Graded SQL path — `sandbox-runtime/engine-core.mjs`

- **Can `stripTrailingSemicolon` (`:164`) let a second statement through?** No, and the
  gate/engine divergence is not exploitable. Three independent reasons: the gate rejects anything
  that does not parse to exactly one statement (`src/lib/sandbox/gate.ts:567`) on the text the learner
  submitted; the function's only possible edit is the _removal_ of one `;`, which cannot create a
  statement; and on the SELECT path the remaining text is wrapped in `select * from ( … ) as
__consulta limit n`, where any surviving `;` is a syntax error rather than a separator. The
  non-SELECT path passes `cleaned` to `pg.query`, which uses the extended protocol (one statement per
  call) — multi-statement execution needs `pg.exec`, and the only `exec` call is the fixed
  `set TimeZone …; set role learner`.
- **Scanner edge cases I probed:** dollar-quoted bodies (`select $$a;$$`) — the `;` is not the last
  code character, so nothing is stripped; the non-standard backslash branch
  (`if (sql[i] === "\\" && c === "'")`) mis-tracks `select 'a\';` under
  `standard_conforming_strings = on`, and the consequence is that the terminator is _kept_ and the
  query fails with a syntax error. Every mis-parse I could construct fails closed.
- **`unwrapErrorPosition` (`:217`) leakage:** it returns a number or `undefined`, never text, and
  returns `undefined` whenever the position lands in the wrapper prefix (`innerOffset < 1`) or past
  the learner's text (`> inner.length`) — fail-closed, as claimed. `innerOffset + leading` is bounded
  by `original.length`, so no out-of-range caret. The wrapper's alias `__consulta` can still appear in
  a Postgres _message_ for some errors, which is pre-existing, carries no secret and is not worth
  changing.
- **`rowMode: "array"` and the caps:** `fields` is still sliced to `limits.maxColumns` and `rows` to
  `limits.maxRows` before projection, and cells are now read positionally over the already-sliced
  field list, so `sanitizeCell(…, limits.maxCellBytes)` sees exactly the same values it did (one per
  capped column). Nothing bypasses a cap; the change makes duplicate output names report their own
  values instead of collapsing, which is a correctness fix, not a widening.
- **Published copy:** identical to source, git-ignored, regenerated by `prebuild`. No stale-asset risk.

### 5. Leaderboard — `20260923121000_leaderboard.sql`

Consent filter `p.leaderboard_opt_in and p.deleted_at is null and p.alias is not null` is inside the
`participants` CTE (`:42`) with no parameter that can reach it; `p_period` only selects between two
XP expressions. A non-participant appears in neither the rows nor the count — `leaderboard_participants`
counts the rows of the same function (`:86`), so the two can never disagree, and the self-row clause
