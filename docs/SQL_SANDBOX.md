# Safe SQL Execution — Analysis and Selected Design

**Decision:** D-03 in [DECISIONS.md](DECISIONS.md). **Status:** approved architecture, not yet implemented (Phase 4).

## 1. Threat model

Learners submit arbitrary text that is executed as SQL. Threats, in priority order:

1. Reading or modifying application data (profiles, entitlements, payments, solutions).
2. Privilege escalation inside the database (superuser functions, `COPY ... PROGRAM`, `pg_read_file`, `dblink`, extensions).
3. Resource exhaustion: infinite recursive CTEs, cartesian joins, `pg_sleep`, huge result sets, many concurrent requests.
4. Persistence/pollution: DDL/DML that changes the dataset for other learners.
5. Answer leakage: obtaining reference solutions or expected results from any payload.
6. Abuse of the endpoint as a free compute service.

Selected: **hybrid D + E**, with B documented as the fallback if PGlite proves too slow or too heavy on Vercel.

Why not only E? Grading in the browser lets anyone forge results, rewards and certificates. Why not only D? Every exploratory run would cost a server invocation and add latency; the browser engine makes exploration instant and free, which matters pedagogically.

## 3. Selected architecture

```
Browser                                  Vercel Node function                 Supabase (app DB)
┌────────────────────────┐   Submit     ┌───────────────────────────┐        ┌────────────────┐
│ CodeMirror SQL editor  │ ───────────► │ 1. auth + entitlement     │ ─────► │ attempts,      │
│ PGlite (Web Worker)    │              │ 2. rate limit             │        │ rewards,       │
│  dataset snapshot      │   result +   │ 3. size + parser gate     │        │ progress       │
│  "Run" = local only    │ ◄─────────── │ 4. PGlite in worker_thread│        └────────────────┘
└────────────────────────┘   feedback   │    (ephemeral, read-only  │
                                        │     role, hard timeout)   │
                                        │ 5. structured validator   │
                                        │ 6. feedback + rewards     │
                                        └───────────────────────────┘
```

**Datasets** are generated by deterministic TypeScript scripts (seeded PRNG) and written as versioned static files: `public/datasets/<slug>/v<n>/{schema.sql, <table>.csv, manifest.json}` (a PGlite data-dir tarball was rejected in Phase 4: ~4.5 MB of base overhead per snapshot). Both engines load them with `COPY … FROM '/dev/blob'` into a fresh in-memory PGlite and then lock it down (`learner` role, denied functions). Measured: TiendaViva (91 k rows, 5 MB CSV) loads in ~6 s in the browser and ~1 s in the server worker; queries then take tens of milliseconds.

Expected results for each exercise are computed at content build time by running the reference solution against the snapshot and stored in the app DB (`exercise_expected_results`), never shipped to the browser.

| 4     | **SQL parser gate** (`pgsql-ast-parser`, pure TS): must parse; exactly one statement; statement kind in the exercise allowlist (SELECT-like incl. WITH/UNION/VALUES; write exercises may add `insert`/`update`/`delete`); DML inside CTEs counts as DML; locking clauses (`FOR UPDATE/SHARE`) rejected anywhere they appear, including inside a scalar subquery, `EXISTS`, `ARRAY(...)` or a named window definition; unparseable statements (`copy`, `set`, `do`, DDL, transaction control, dollar quoting) rejected; references to schemas outside `public` rejected. Because `pg_catalog` is implicitly first in `search_path`, an explicit-schema check alone is not a system-catalog control. A catalog read has **three spellings**, and the gate rejects all three: the **relation** (`select * from pg_settings` — any unqualified relation name starting with `pg_`, and one literally named `information_schema`), the **cast** (`::regclass`, `::regnamespace`, `::regrole`, `::regproc`, … — the eleven OID alias types, listed in `sandbox-runtime/denied-functions.mjs`), and the **function** (`pg_show_all_settings()`, which returns the same 380 settings as `pg_settings`; `pg_get_userbyid()`; `to_regclass('customers')`; and an alias type written in function syntax, `regclass('customers')`, which PostgreSQL parses as a cast). Function names are denied **by prefix** — `pg_` and `to_reg`, unqualified or `pg_catalog`-qualified — not by enumeration, so a function added by a future PGlite is covered without an edit; the same prefixes drive the layer-5 `REVOKE` (SEC-06 and SEC-08 in `docs/reviews/2026-09-23-security.md`, decisions D-21 and D-22). Cast targets (`ExprCast.to`, including array element types) are checked for schema as well. What the three rules do **not** cover: a catalog relation or function whose name matches none of these prefixes — this is a name-based control at layer 4, and how much layer 5 holds behind it depends on the spelling. For the **function** spelling it holds (EXECUTE is revoked). For the **relation** spelling it mostly does **not**: PostgreSQL grants `SELECT` on most catalogs to `PUBLIC`, so `pg_class`, `pg_proc`, `pg_roles` and `pg_tables` are still readable by `learner` after `lockDown()` (verified 2026-09-22 on PGlite 0.5.8 / PG 18.3); only the restricted few (`pg_authid`, `pg_shadow`, `pg_statistic`, `pg_file_settings`) and `information_schema` (its views call the now-revoked `pg_has_role`) fail on permissions. What makes the relation rule complete today is not layer 5 but the naming convention: every relation in this engine's `pg_catalog` is named `pg_*` (verified: zero exceptions), so the gate's prefix covers all of them. The instance is ephemeral and holds only the exercise dataset, so what a catalog read can expose is dataset metadata, role names and engine settings — no learner data and no secrets. Nothing a learner legitimately writes is rejected: no dataset table in the four snapshots is named `pg_*`, no authored exercise calls a `pg_*`/`to_reg*` function, the alias block is an exact-name match (so `region`, `registro`, `regexp_*` and the `regr_*` aggregates are unaffected), and table aliases, CTE bodies and column names are not relation names. A CTE _named_ `pg_x` is rejected, deliberately, and the Spanish message says the prefix is reserved (SEC-09). `pg_authid`/`pg_shadow` and `current_setting` remain denied by layer 5 regardless; denied functions rejected (list in `sandbox-runtime/denied-functions.mjs`, shared with the engine lockdown). Known parser gap: window frame clauses (`ROWS/RANGE/GROUPS BETWEEN …`) are not understood by `pgsql-ast-parser`; the gate blanks them (same-length whitespace, closed grammar so nothing else can hide inside) before parsing and always executes the original SQL. Frame bounds accepted by that blanking are `UNBOUNDED PRECEDING/FOLLOWING`, `CURRENT ROW`, a numeric offset and an interval offset (`INTERVAL '6 days' PRECEDING`, `'6 days'::interval PRECEDING`), whose only variable part is a complete single-quoted literal. Second known parser gap: `INTERSECT` / `EXCEPT` have no grammar in `pgsql-ast-parser`; `normalizeSetOperators()` rewrites them to a same-length `UNION` variant for analysis only (never inside literals or comments) and the original SQL is executed — see D-18 in `docs/DECISIONS.md`. Third known parser gap: named windows (`WINDOW w AS (...)` / `OVER w`); `rewriteNamedWindows()` blanks the clause and rewrites `OVER w` to a same-length `OVER ( )`, and every blanked definition is parsed and analysed separately (`select count(*) over (<definition>)`) so denied functions, system schemas and subqueries inside it are still rejected and still appear in `gate.functions`. Fourth known parser gap, and the one that has bitten repeatedly: `AstDefaultMapper` does **not** descend into every node, so learner SQL in those positions would reach the engine unanalysed. The gate therefore visits them explicitly, in the same `astVisitor` pass and always **before** delegating to `map.super()` (the library's `skipNext` flag makes the reverse order unsafe): `ExprCall.over` (PARTITION BY / ORDER BY), `SelectFromStatement.distinct` (`DISTINCT ON (...)`), `FromCall.join.on` (the `ON` predicate of a JOIN hanging off a set-returning function), `ExprRef.table` (a schema-qualified column reference), `OnConflictAction.where` and `ExprCast.to` (the target type of a cast). Fields that are unvisited but carry no expression and no statement (`ExprBinary.opSchema` / `ExprUnary.opSchema`, `OnConflictOnConstraint.constraint`, `SelectFromStatement.skip`, `JoinClause.using`, `FromCall.withOrdinality`) are inventoried in the header of `tests/sandbox/traversal.test.ts`. See D-19 and the review in `docs/reviews/2026-09-23-security.md`. Controlled **write exercises** (post-MVP): exercise metadata declares `allowed_statements`; a fresh ephemeral instance is used and discarded, so rollback is implicit; validation runs a follow-up `SELECT` defined by the exercise.

## 5. Browser engine specifics

- PGlite runs in a static module Web Worker (`public/sandbox-worker.js`) that imports PGlite's own dist files served from `public/pglite/` (copied by `npm run assets:pglite`, ~5 MB gzipped, one-time, browser-cached) and the shared `engine-core.mjs`; strict CSP holds (`worker-src 'self'`). The worker is terminated and recreated on timeout.
- Dataset CSVs are fetched from `public/datasets/` (~1.2 MB gzipped for TiendaViva). IndexedDB persistence of the loaded database is a post-MVP optimization.
- Run results carry the banner "Vista previa local. Envía tu consulta para validarla."
- If WASM init fails (old browser, low memory), Run falls back to the server engine with a stricter rate limit.

## 6. Known limitations and accepted risks

- PGlite is single-connection; concurrency inside one function instance uses a small worker pool (default 2) and a queue.
- Cold start on Vercel adds 0.3–1 s on the first Submit per instance; acceptable for graded submissions.
- Datasets must stay modest (tens of thousands of rows); expert exercises can use dedicated larger snapshots.
- If measured Submit p95 > 3 s in Phase 4 load tests, switch the server engine to fallback B while keeping E in the browser. The executor interface is provider-agnostic: `SandboxEngine.execute(datasetRef, sql, limits)`.
- **`EXPLAIN` cannot be submitted.** `pgsql-ast-parser` has no grammar for it, so `gateSql` returns `parse_error` at the keyword before the statement-kind allowlist is consulted; widening an exercise's `allowed_statements` cannot help. PGlite itself runs `EXPLAIN (ANALYZE, BUFFERS)` fine, so this is a gate limitation, not an engine one. Sections 34 and 35 were authored around it — they teach plan reading from plans captured in the lesson text, and section 34 says plainly that the sandbox cannot run `EXPLAIN`. Lifting it needs a leading-`EXPLAIN` strip for analysis only (same shape as the `INTERSECT`/`EXCEPT` and window-frame rewrites) plus an `explain` statement kind; owner `sql-sandbox-engineer`, not started.

## 7. Validation gates before Phase 4 sign-off

- Fuzz suite of ≥ 200 malicious inputs (`tests/sandbox/malicious.sql`) must all be rejected or fail harmlessly.
- Timeout test: a `WITH RECURSIVE` bomb is killed within 5 s and the function stays healthy.
- Load test: 50 concurrent submits stay under function memory limits.
- Static check: no module that imports `@electric-sql/pglite` may import the Supabase secret client.

## Session settings

- **`TimeZone` is pinned to `UTC`** in `sandbox-runtime/engine-core.mjs` (`SANDBOX_TIME_ZONE`),
  applied as a database default and on the session at dataset load, and re-applied on the session
  immediately before every graded statement. PGlite otherwise takes the zone from the host at
  initdb — `Etc/GMT+3` on the owner's machine, `Etc/GMT0` on CI and Vercel — and `timestamptz`
  arithmetic is resolved in the session zone, so an unpinned engine grades the same correct query
  differently depending on where it runs. This was not theoretical: three exercises shipped with
  expected results generated at `Etc/GMT+3` that a UTC learner could not reproduce (D-20).
- That file is the **only** PGlite setup path. The browser Web Worker loads a byte copy published
  to `public/sandbox-core/` by `scripts/copy-pglite-assets.ts`, the server `worker_threads` worker
  imports it directly, and `scripts/content-verify.ts` imports it directly. Pin session state there
  and nowhere else; a `SET` added at one call site will silently not apply to the other two.
- Re-applying the zone per statement is deliberate. The load-time pin is not enough on its own to
  reason about: the graded statement is the one whose value is compared against a stored expected
  result, so the setting is guaranteed at that point rather than inherited.
- Verified per path by `tests/sandbox/timezone.test.ts`, which asserts both `SHOW timezone` and a
  zone-sensitive result (`TIMESTAMPTZ '2025-07-01 00:00:00+00' + INTERVAL '1 month'`). Asserting
  the setting alone would not have caught a path that never runs the `SET`.
- On a deployment, `GET /api/health/sandbox` (CRON secret) reports the zone the graded engine
  actually observes and returns 503 if it is not UTC.
- Changing the pinned zone invalidates every stored expected result: `npm run content:verify` must
  be re-run and the diff reviewed by `content-author`, because expert explanations quote numbers.

## The SELECT wrapper (`runLearnerQuery`)

SELECT-like statements are executed as `select * from (\n<learner sql>\n) as __consulta\nlimit n+1`, so
an unbounded result is never materialized. Everything the wrapper adds is on its own line, and the
statement terminator is removed by `stripTrailingSemicolon()`, which skips literals and comments.
Both details are load-bearing and were bugs:

- With the closing paren on the same line, any query ending in a `--` comment commented it out and
  failed with a syntax error about a character the learner had every right to write.
- `/;+\s*$/` only anchored at the end of the string, so `select 1; -- nota` kept its semicolon and
  produced `syntax error at or near ";"`. The gate accepts that input (one statement plus a
  comment), so the engine has to as well.

`position` from PostgreSQL refers to the wrapped statement; `unwrapErrorPosition()` shifts it back
by the wrapper prefix (plus the leading whitespace `trim()` removed) and returns nothing when the
position lands in the wrapper's own text, so the editor never underlines the wrong character.

Rows are read with `rowMode: "array"`. In object mode two columns with the same output name
(`select id, customer_id as id from orders`) collapse into one key and the second value was
reported for both, i.e. the comparator graded values the engine never returned.

Reviewed independently in security review 2026-09-23 and confirmed: every mis-parse constructed
against `stripTrailingSemicolon` (dollar quotes, the non-standard backslash branch on `select 'a\';`)
fails **closed**, by keeping the terminator, and the gate's single-statement rule means no second
statement can reach the engine either way; `unwrapErrorPosition` returns a number or `undefined` and
never text; `rowMode: "array"` preserves every row, column and cell cap.

Audited and unchanged by the wrapper: `ORDER BY` inside the subquery (PostgreSQL preserves it under
a plain `select * … limit`), the learner's own `LIMIT`/`OFFSET` (applied inside, before the cap),
`WITH`, `VALUES`, set operations, trailing block comments and a semicolon inside a comment. A query
that is only a comment never reaches the engine — the gate rejects it (zero statements). Cases in
`tests/sandbox/wrapper.test.ts`.

## Comparator feedback when the values differ

When the row count matches and the values do not, `compareResults` no longer reports a count of
mismatching rows — the old message ("… 18 filas esperadas no aparecen") read like a row count and
sent the owner looking for a phantom engine bug. `describeValueDifferences()` instead:

1. names the columns whose value sets diverge (`cell_values`, param `columns`);
2. pairs each actual row with its expected row on the columns that _do_ match (falling back to
   position) and, if one constant ratio or offset explains every differing value in the first
   differing column, reports that (`cell_values_scale_smaller` / `_larger`, `cell_values_offset_low`
   / `_high`) — a missing `* 100` is diagnosed in one sentence;
3. otherwise quotes one pair of values, the learner's and the expected one, for that column
   (`cell_values_example`). Disclosure is deliberate: one cell of one row, in a result whose column
   names the learner already has from `expected_columns`, and strictly less than the whole expected
   row this finding used to carry.

The expected value is withheld — only the learner's own value is reported, via
`cell_values_example_actual` — in three cases:

- the result is a single cell (one row, one comparable column), where that value _is_ the answer;
- the submitted projection is **narrower** than `expected_columns`;
- **no comparable column matched**, so the two rows were paired by position rather than by a key.

The last two close security review 2026-09-23 **F-4**: with nothing to pair on, the example returns
row 1's expected value; feeding it back moves the mismatch to row 2, so the whole expected result can
be read out one submission at a time (~72 submissions for 4 columns × 18 rows, inside
`rateLimits.submit`). Requiring the learner to have attempted the full shape of the answer costs an
honest attempt nothing — it selects every expected column and usually gets the key column right —
and a positional pair is also the case where a quoted expected value is least trustworthy as
feedback. Residual and accepted: someone who reproduces the key columns exactly (most of the work of
the exercise) still gets one expected cell per submission for the remaining columns. The loop is
walked in `tests/unit/compare-cell-values.test.ts` ("F-4 — the expected value cannot be iterated out
of the comparator"), which fails if the guard is removed.

The scale/offset hint is unaffected: it never quotes an expected value, which is why it takes
precedence when it fires.

## Style feedback from the learner's query

`src/lib/validation/style.ts` derives non-blocking style and good-practice items from the submitted
SQL (`detectStyleIssues`); `buildFeedback` orders them by the list in that file, caps them at
`limits.sandbox.feedback.maxStyleItems` and appends the learner's own query re-indented
(`formatSql`, message key `improve.formatted_version`) when a re-indent is possible. `formatSql` is
token-based and verifies itself by parsing input and output with `pgsql-ast-parser` and comparing
the trees; it returns `null` rather than guess (queries with comments are never formatted).

The governing rule is that a tip which fires on good SQL is worse than a missing tip:
`tests/unit/style.test.ts` asserts that no check fires on any authored reference solution. Two
checks were removed for failing it — divisor-without-`nullif` (38 reference solutions) and
function-wrapped columns in `WHERE` — and three were narrowed (indentation, `ORDER BY <n>`,
single-letter aliases); the reasons are recorded next to each function. Style items never affect
grading: `correct` comes from the comparator and blocking items only.

## Grading path and the published-solutions guard

`gradeSubmission` (`src/lib/validation/grade.ts`) is the whole verdict for one submission: engine
execution, comparator against the stored expected result, `buildFeedback`. `submitExercise` calls
it and nothing else decides `correct`. `tests/sandbox/reference-solutions.test.ts` sends every
exercise's reference and alternative solutions through that same function, on the real
`worker_threads` engine, against `supabase/seed/0003_expected_results.sql` (what production
holds), and fails on any published solution graded wrong, including a timeout. It closes two
gaps `content:verify` leaves open: verify compares alternatives with the comparator only (not with
`required_concepts`, `prohibited_patterns` or the hard timeout), and it regenerates the seed
instead of checking the committed one.

Alternatives whose result matches but that lack a concept in the exercise's `required_concepts`
are listed in that test as a quarantine (exact match; fixing one means removing its entry). Each is
a content decision (drop the requirement, or drop or relabel the alternative), not a grader fix.

The `date_boundary` warning (`<= 'YYYY-MM-DD'` or `BETWEEN` with bare dates on a timestamp) fires
whenever the row count differs and the exercise lists that mistake, with no size threshold: a
lost final day can be well over 5 % of a short range (owner feedback round 6, item 11).

## Runtime notes

- `@electric-sql/pglite` is listed in `serverExternalPackages` (next.config.ts) and the worker lives in `sandbox-runtime/`, outside `src/`. Bundled, PGlite resolves to a build whose wasm loader throws `instantiateWasm is not a function`, so the graded engine never booted under `next start` — every submission came back as an engine error while every local test passed. `GET /api/health/sandbox` (bearer `CRON_SECRET`) executes one query through the real engine and is the fastest way to confirm a deployment.
- The worker is spawned with `execArgv: []` and imports PGlite through an absolute path resolved with `createRequire(...).resolve()`. Under `next start` the worker inherited Next's module loader and a bare `@electric-sql/pglite` specifier resolved to a bundled `.next` chunk, whose wasm/data lookups fail with `ERR_INVALID_ARG_TYPE` — the engine never booted and every graded submission returned an engine error.
- The worker imports `sandbox-runtime/native-url.mjs` first: Next.js installs its own global `URL` in the server runtime and the worker inherits it, so PGlite's `new URL(..., import.meta.url)` lookups were rejected by `fs` ("must be ... an instance of URL. Received an instance of URL") and the engine never booted — every graded submission came back as an engine error. Restoring the native class before PGlite is evaluated fixes it.
- Boot failures are logged (`[sandbox] worker fatal/error`); they used to be swallowed, which is why the cause was invisible in CI.
- Node 24 everywhere (local, CI, Vercel); see `package.json` engines.
